# Evidence Workflow

Use this guide when the source set is large, inconsistent, or mostly early-career material.

## Source priority

Prefer, in order:

1. Current user statement that corrects an old record.
2. Original certificates, offer letters, contracts, transcripts, published repositories, releases, screenshots, or reports.
3. A supplied resume or portfolio with traceable underlying work.
4. Old notes, AI summaries, search history, and plans.

When sources conflict, use the most recent explicit correction and list the discrepancy in the review file. Do not silently choose the more impressive version.

## Evidence matrix

Maintain a compact matrix:

| Claim | Status | Evidence | Usable wording | Caveat |
|---|---|---|---|---|
| Project shipped a feature | confirmed | Release link / demo | Built and verified... | State scope if prototype |
| Improved efficiency by 30% | needs check | No baseline found | remove metric | User must supply measurement |
| Knows Kubernetes | not usable | Only installed tutorial | omit | No project evidence |

Useful status labels:

- `confirmed`
- `user-confirmed`
- `needs check`
- `inferred`
- `not usable`

## Claim strength

Separate these levels:

- Installed or attended
- Studied or practiced
- Built with guidance
- Built independently
- Tested or deployed
- Operated in production
- Owned an outcome or team

Use wording that matches the actual level. A small prototype can still be valuable; calling it a production system without evidence is not.

## Students and early-career candidates

Lead with education only when it is a real screening advantage. Otherwise lead with projects, internships, competitions, open-source work, or demonstrable skills. Treat coursework as evidence of applied capability, not professional employment.

For team projects, state the candidate's actual contribution. For competitions, include the awarding body, level, track, time, and result only when verified.

## Career switchers

Translate prior work into transferable evidence without renaming the occupation. Show why the transition is credible through projects, outcomes, domain knowledge, or training.

## Certificates and tool lists

A certificate proves completion of the named assessment, not mastery. Mention only the certificates relevant to the target and keep the official name. Do not add a certificate category unless it helps the target reader.

## Sensitive information

Defaults:

- City is enough; omit a street address.
- Show phone and email only when the user wants them on the resume.
- Omit birthday, ID number, marital status, health data, and photograph unless the local convention or employer explicitly requires it.
- Do not include proprietary data, customer names, source code, or internal metrics that the person is not allowed to disclose.
